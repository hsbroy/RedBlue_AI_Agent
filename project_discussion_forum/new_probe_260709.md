## 一、為什麼要做新探針？（背景動機）

初賽審查委員的核心批評，直接點出我們目前架構的弱點：

> 「本質上是『使用既有工具（NVIDIA Garak + NeMo Guardrails）跑掃描 + 把結果做成過濾規則』的工程作業，**原創性偏弱**——Garak 本身就是 NVIDIA 開源工具，提案的核心增量（特徵提取、規則生成、Gateway 部署）具體演算法沒展開。」
>
> 「建議可多著墨在**攻擊提示詞的創新**或防護規則的產生技術，以確認實務上的可行性。」

**結論**：目前直接呼叫 Garak 內建探針（`promptinject`、`dan`、`continuation` 等）不足以證明我們有原創貢獻。這些探針幾乎都是**英文語境**設計，我們需要自己設計「新探針」來填補空白、產出量化證據，證明專題有實質技術產出，而不只是工具串接。

## 二、三個候選方向比較

| 面向 | A. 繁中/台灣語境探針 | B. 自動變異探針 | C. 多輪漸進式探針 |
|---|---|---|---|
| **核心概念** | 針對 Garak 探針庫的英文語境空白，設計中文專屬攻擊：諧音字替代、繁簡轉換、中英夾雜、台灣網路黑話包裝 | 攻擊被藍方擋下後，紅方 LLM 讀取阻擋原因，自動重寫語意相同但避開觸發詞的新變種，反覆迭代直到成功或達上限 | 利用 `create_agent` 的多輪記憶，設計「先鋪陳無害情境 → 逐輪升級 → 最後提出違禁請求」的跨輪次攻擊 |
| **對應審查意見** | 直接回應「攻擊提示詞的創新」；可產出量化對比數據（英文原版破防率 vs 中文變體破防率） | 直接回應「AI Agent 自動化控制的具體決策邏輯沒交代」；概念上對應學術界 PAIR/TAP 演算法，理論含金量較高 | 間接但很犀利——會暴露我們現有藍方架構的**真實漏洞**（見下方） |
| **技術複雜度** | 低：不用動 Garak 核心，純粹設計 prompt 樣板 + 建立對照測試 | 中高：需重構 `red_tools.py`，拆出「單次攻擊」與「迭代迴圈」邏輯，設計變異紀錄的資料結構 | 中：Garak CLI 本身單輪、無狀態，多輪必須繞過 CLI，自己寫對話迴圈直接呼叫 Ollama API |
| **對現有小模型（qwen2.5:3b）的依賴度** | 低：樣板可人工設計，不需要模型即時創造力 | **高**：小模型的「改寫規避偵測」能力可能不足，變種品質可能不理想（但這也可以是一個研究發現） | 中：模型只需照劇本走多輪對話，不需臨場創造攻擊 |
| **剩餘時間內完成機率** | 高 | 中（架構重構風險 + 可能跑不出漂亮數據） | 中高 |
| **可產出的量化證據** | 「中文變體破防率比英文原版高 X%」→ 直接證明填補真實空白 | 「平均需 N 次迭代才能繞過藍方」+「哪些變異策略最有效」 | 「單輪審查漏擋率 vs 多輪審查漏擋率」 |

## 三、一個已發現的既有架構漏洞（跟方向 C 直接相關）

檢查 `main.py` 目前邏輯：

```python
blue_inputs = {"messages": [HumanMessage(content=user_question)]}
blue_result = blue_agent_executor.invoke(blue_inputs)
```

**藍方每一輪只看「這一輪」的輸入，完全沒有帶入對話歷史。**

代表：如果攻擊者「先聊無害的事鋪陳情境，最後一輪才問違禁問題」，藍方看到的永遠只是「最後一句話」，可能因單獨看起來無害而放行——即使前面幾輪已明顯在鋪陳越獄情境。

這個漏洞**不需要完整做完方向 C 的探針設計就能先驗證**（花半天測 2-3 組漸進式對話即可），且正好呼應審查意見「防護規則的產生技術，以確認實務上的可行性」。

## 四、建議執行順序

1. **優先做 A（繁中探針）**
   ROI 最高、風險最低、最快產出量化數據，適合當作「新探針」主力交付物，短時間內看得到成果，對論文進度最保險。

2. **順便驗證上述藍方多輪漏洞**（不用做完整方向 C）
   花少量時間測試漸進式對話是否真的漏擋。若驗證屬實，就是一個現成、犀利的「架構層級發現」，可直接寫進論文作為「透過紅方測試發現的防禦盲點」，順勢帶出防禦改進方向。

3. **方向 B 留到最後當加分項**
   若 A 與漏洞驗證都完成且還有餘裕，再挑戰自動變異迴圈。技術含金量最高，但風險也最大，不建議把主力進度押在這裡。
